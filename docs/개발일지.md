## 왜 이렇게 했나

- **pptx 를 새로 그리지 않고 직전 파일을 고쳐 씁니다.** 회사 양식에는 마스터 · 테마 · think-cell · 태그처럼 도구가 다시 그릴 수 없는 것이 많습니다. 표 칸(a:tc)의 글자만 바꾸고 첫 글자의 모양(크기 · 굵기 · 색 · 글꼴)과 칸 테두리 · 채우기를 그대로 두면 「내용만 바뀐」 보고서가 됩니다.
- **2장은 첫 차이 슬라이드를 본으로 삼아 모두 다시 만듭니다.** 견본에는 차이 슬라이드가 2장(창고 위치명 · 창고위치명2)인데 이번 달 창고 수와 품목 수는 다릅니다. 첫 장을 본으로 창고 · 쪽 수만큼 복제하고 원래 차이 슬라이드는 모두 지워야, 만든 보고서를 다음 달에 다시 올려도 같은 결과가 납니다(검사 「다시 넣기」).
- **한 장 줄 수는 직전 표의 가장 낮은 줄 높이로** 셉니다(견본 9줄). 긴 사유 · 자재내역은 칸 너비 · 줄 높이에 맞춰 「…」 로 줄입니다 — 줄이 늘어나면 PowerPoint 가 행을 키워 표가 슬라이드 아래로 나갑니다. 전체 글은 결과서 엑셀 「차이 상세」에 있습니다.
- **실사 현황 표의 행은 직전 표의 행 이름으로 고릅니다.** 견본은 머리가 「창고위치」인데 행 이름이 자재타입이라 어느 쪽인지 단정할 수 없어, 이름이 맞는 기준을 쓰고 화면에서 바꾸게 했습니다. 직전 이름은 그 달에 품목이 없어도 「-」 로 남깁니다(보고서끼리 줄이 맞아야 비교가 됨).
- **빨간 글자는 「0 이 아닐 때」** 입니다. 메모의 「0 이상」을 글자대로 하면 차이 0 도 빨강이 됩니다. 도구가 칠하는 빨강(FF0000)만 다시 걷어 내게 해서, 양식에 원래 있던 색은 건드리지 않습니다.
- **XML 을 DOM 없이 문자열로** 다룹니다. 같은 코드가 node 검사에서도 돌아야 하고(의존성 0), 표 · 도형 요소는 겹치지 않는 구조라 짝 세기로 충분합니다. 대신 꾸러미 검사기(XML 짝 · 관계 대상 · Content_Types · id · 노트 공유 · app.xml)를 테스트에 넣었습니다.

## 왜 이렇게 했나

- **「저장위치」를 창고로** 읽었습니다. 견본에서 저장위치(코드)와 저장위치명이 짝이고, 창고 안 자리는 Location 이 따로 있습니다. 1단계 별칭은 저장위치를 보관 자리로 읽어 견본이 「창고위치(사내/사외)」를 창고로 잡는 엉뚱한 결과가 났습니다. 다만 다른 ERP 에서는 저장위치가 보관 자리일 수 있어, 「창고」 열이 따로 있으면 예전처럼 돌립니다.
- **SharePoint 를 버리지 않고 그 자리에 맞췄습니다.** 지금 이미 취합 파일 하나에 각자 적는 습관이 있고, 회사가 허용한 공유 공간입니다. 그래서 도구가 내는 파일을 곧 SharePoint 취합 파일로 만들고, 그 파일을 다시 넣으면 합쳐지게 했습니다. 이 도구가 처음부터 끝까지 서버 없이 돌면서도 「여러 사람이 한 파일에」가 됩니다.
- **기록 ID 를 내용으로** 만들었습니다(재고번호 · 작성자 · 수량 · 사유 · 확인시각). SharePoint 파일은 하루에도 여러 번 내려받아 넣게 되므로, 넣을 때마다 같은 줄이 또 들어가면 안 되고, 고친 줄은 정정으로 남아야 합니다. 휴대폰 기록을 엑셀로 냈다가 다시 넣는 경우도 같은 규칙으로 걸러집니다.
- **차이수량은 견본 방향(수량 − 실물)** 그대로 엑셀 수식으로 넣었습니다. 현장에서 쓰는 종이 양식과 같아야 헷갈리지 않습니다. 화면 분석은 1단계대로 실물 − 시스템(증가 · 감소 금액)이라, 화면과 지시정보에 두 방향을 적고 수강생에게 확인을 요청했습니다(10장 남은 확인 2).
- **허용 0 이어도 「허용 범위」를 지우지 않았습니다.** 회계감사 보고에서 금액 기준을 따로 볼 수 있어 선택으로 남겼고, 어느 쪽이든 사유 필수는 바뀌지 않습니다.

## 사고와 교훈

- **배정표 「실사인원」 열을 못 읽었습니다.** 머리 글자를 맞출 때 끝의 단위(개 · 원 · EA …)를 떼는데, 「실사인원」의 「원」이 단위로 떼여 「실사인」이 되었습니다. 그래서 실사인원 0 인 창고가 제외되지 않았습니다. 실제 견본으로 돌려 보다가 잡았고, 배정표는 원래 글자로도 견주게 고쳤습니다. 검사에 「실사인원이 모두 읽혀야 함」을 넣고 고친 줄을 되돌리면 7개가 실패합니다.

- **「실시간 취합」은 1단계에서 파일 합치기로** 했습니다. 정적 웹은 기기마다 저장하므로 휴대폰끼리 바로 섞이지 않습니다. 실시간을 하려면 서버(공유 DB)가 필요한데, 회사가 외부 클라우드를 허용하는지 모르는 상태에서 붙이면 쓰지 못하는 기능이 됩니다(10장 ⑤). 대신 기록마다 고유 ID 를 두어 결과 파일을 여러 번 보내도 한 번만 들어가게 했고, 같은 구조로 DB 초안을 미리 잡아 두었습니다.
- **충돌과 정정을 나눴습니다.** 같은 사람이 다시 센 것은 정정(마지막 기록), 다른 사람끼리 수량이 다르면 충돌(실사 담당자가 고름). 둘을 같이 「충돌」로 보면 정정할 때마다 사무실 일이 생깁니다. 검사에서 이 구분을 지우면 4개가 실패합니다.
- **사유는 인벤토리 04 의 6개 그대로** 썼고, 차이가 있으면 반드시 고르게 했습니다(「기타」는 특이사항 필수). 종이 기록 엑셀에서 사유가 빈 차이는 「사유 미입력」으로 따로 세어 보고서에서 빠지지 않게 했습니다.
- **허용 기준은 「차이율 또는 금액」** 입니다. 볼트처럼 싸고 많은 품목은 차이율이, 완제품처럼 비싼 품목은 금액이 걸리게 하려는 것입니다. 시작값(2% · 10만 원)은 임시 값이고 10장 ③ 확인 대기입니다.
- **AI 프롬프트에는 담당자 이름을 별칭으로**, 자재코드·자재명은 기본으로 넣지 않습니다. 실사 결과는 회계감사 자료이고, 요약·개선 제안에는 창고·유형·타입·숫자로 충분합니다.
- **사진은 800px JPEG 로 줄여** 기록에 넣습니다(1장 50~100KB). 브라우저 저장 공간(보통 5MB 안팎)이 금방 차므로 화면 위에 저장 용량을 늘 보여 주고, 결과 파일에는 사진을 고를 때만 넣습니다. 2단계에서는 DB 가 아닌 비공개 저장소에 둡니다.

## 사고와 교훈
